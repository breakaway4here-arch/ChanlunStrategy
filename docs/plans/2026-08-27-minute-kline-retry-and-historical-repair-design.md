# 分钟行情重试与 2026-08-26 历史修复设计

## 1. 结论

本次同时解决两个问题：

1. 正式日报拉取 15/30 分钟行情失败时，执行“首次请求 + 3 次重试”，每次只请求一个数据源，按 `Eastmoney -> Sina -> Eastmoney -> Sina` 轮换；四次均失败后将该股票标记为不可用，旧数据库或旧 JSON 只能保留为诊断证据，不能进入选股。
2. 2026-08-26 只使用真实历史分钟线重建受影响的正式候选。重建结果在页面可见，但明确标注“历史重建、不计原始发布样本”，不得追写成当日已经发布的推荐，也不得进入策略绩效账本。

`picks_pure` 仍是所有策略共同上游全集。各策略保留独立筛选逻辑，不统一门槛、不按数量补票。

## 2. 已确认根因

- 2026-08-26 日线和大盘数据正常，`picks_pure` 有 136 只，融合池中只有 `300697 电工合金` 达到正式推荐决策。
- 当日 30 分钟数据库最新日期停在 2026-08-24；旧流程只检查 K 线数量，不检查“报告日、已收盘、非旧缓存”。
- 分钟行情获取同时请求两个数据源一次，任一返回非空就结束，没有重试，也没有在入库前校验报告日。
- `300697` 因此使用了截至 2026-08-21 的旧 30 分钟确认。后续 fail-closed 修复正确隐藏了该推荐，导致页面正式主推为 0。
- 2026-08-27 使用新浪真实 30 分钟历史数据回看，2026-08-26 15:00 数据存在，且仍满足 `30min EMA5维持`；因此可以做有证据的历史重建。
- 强势启动和趋势延续两个升级通道没有把 `strategy_input_evidence` 传到最终候选，导致即使分钟线有效，正式输入健康合同也可能无法证明。

## 3. 正式运行合同

### 3.1 请求次数与数据源

- 单个 `(股票, 周期)` 最多四次 HTTP 请求：一次首次请求、三次重试。
- 15/30 分钟正式窗口均不超过新浪 240 根限制时，顺序固定为：东方财富、新浪、东方财富、新浪。
- 成功取得合格数据后立即停止，不再请求后续数据源。
- 重试间隔为 0.5、1.0、2.0 秒；批量股票继续使用现有有界线程池。

### 3.2 每次响应的入库前门禁

响应同时满足以下条件才可入库：

- 必需数组非空且等长；OHLCV 为有限数值，价格关系合法。
- 根数满足本次请求窗口。
- 指定 `required_date` 时，最后一根日期必须等于报告日，不能早于或晚于报告日。
- 正式收盘选股的 15/30 分钟最后一根必须精确到报告日 `15:00:00`；同日 `14:30` 仍按不完整数据拒绝。
- 最后一根必须是已完成 K 线；15/30 分钟时间戳按 bar end 解释。
- 不合格响应按失败处理并进入下一次重试，不能先写数据库再依赖下游过滤。

四次均失败时返回 unavailable。已有旧数据库记录可以随诊断返回，但其状态必须保持 `stale_cache/preview/missing`，选股批处理继续 fail-closed。

### 3.3 证据传递

所有依赖分钟级确认的候选必须携带：

```json
{
  "strategy_input_evidence": {
    "interval": "30m",
    "status": "verified",
    "latest_date": "2026-08-26",
    "latest_ts": "2026-08-26 15:00:00",
    "source": "market_history_db",
    "bars": 80,
    "stale": false,
    "is_final": true
  }
}
```

候选升级通道只能传递采集层已经核验的证据，不能自行把缺失证据补成 verified。

## 4. 15:20 增量补跑

15:20 不重新抓取已核验股票，只重试 `selection_input_health.sublevels` 中仍为 missing、stale 或 preview 的代码。增量补跑仍执行相同的四次请求上限与新鲜度门禁。

如果残差仍不可用：

- 对应正式策略不可发布动作；
- 允许真实空池；
- 页面必须明确显示数据不可用原因，不能解释成“市场无机会”；
- 禁止旧数据兜底和按数量回填。

## 5. 2026-08-26 修复合同

### 5.1 数据来源

- 通过真实东方财富/新浪分钟行情接口获取历史窗口。
- 原始响应先写入隔离的 staging 数据库，通过日期、终局性、结构和数值校验后再合并到 canonical SQLite。
- 重建查询必须设置 `as_of=2026-08-26 15:00:00`，确保 2026-08-27 及之后的数据不可见。

### 5.2 重建范围

- 只重算已知受 30 分钟旧数据影响的正式候选 `300697` 的次级别确认和输入证据。
- 保留原始日线、市场、事件和上游候选快照，不用当前板块或新闻替换历史事实。
- 其他独立事故（H4 上游合同、罗姐池 15 分钟输入）继续保持不可用，不借本次修复顺带伪造为健康。

### 5.3 页面与账本语义

修复结果放在独立的 `historical_reconstruction` 复盘区，并展示证据日期与数据源。它满足“如果当时分钟行情正常取得，策略会如何输出”的研究问题，但不进入任何正式/研究选股池：

- `is_formal_recommendation=false`
- `scorecard_eligible=false`
- 不追写 2026-08-26 永久推荐账本
- `picks_pure`、`picks_fusion`、`workspace`、`selection_input_health`、影子评测、记分牌和比较索引保持原样
- 当日正式推荐仍显示原始事实 0 只；复盘区另行说明 1 只原始候选因分钟输入未核验被封闭

报告新增重建收据，记录原始正式投影 SHA、数据获取时间、验证代码、数据源和 canonical DB 证据摘要。正式摘要计算明确排除该复盘 overlay，原 production guard 不重写、不自证。

## 6. 发布门禁

上线必须同时满足：

1. 重试、轮换、提前停止、四次上限、旧数据隔离用例通过。
2. 强势启动和趋势延续候选均能传递真实输入证据。
3. 历史修复在 staging 上生成相同的候选身份和证据日期；已存在 overlay 时拒绝重复修复。
4. 2026-08-26 页面在独立复盘区显示重建标记，策略记分牌不增加该样本。
5. 原子发布前后四个报告平面的原始快照、manifest 和比较索引逐项一致。
6. 完整测试通过，远端 `main` 包含修复提交。
7. Pages 在线 JSON、首页和归档页回读一致。
8. 主工作区 LaunchAgent 运行路径已安全同步到远端版本，现有未提交改动未丢失。
