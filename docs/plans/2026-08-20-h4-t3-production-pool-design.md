# H4 T+3 生产池设计

## 目标

把冻结的 H4 T+3 K30 tail-safe 规则接入现有每日选股和报告链。H4 池收录当日全部满足条件的候选，不设数量上限、不回填；候选继续使用现有统一综合分排序，达到现有主推条件时可进入主推，H4 标签本身不额外加分。

## 方案选择

采用“精简冻结训练集 + 当日真实候选实时计算”。从已验证的研究输入导出 H4 所需的延续微状态训练向量、T+3 收益和到期日，作为小型只读模型数据随代码发布。每日任务只读取当日 `picks_fusion`，计算同一套 148 维向量并运行 K30 预测。

不采用以下方案：

- 每日加载完整研究链和 1.5GB SQLite：运行重、依赖多，不适合日报任务。
- 外部预计算后注入页面：不能保证每日任务真实执行，也会再次形成展示与计算脱节。

## 数据流

1. `run.py` 完成 `fusion_scored` 后调用 H4 池构建器。
2. 构建器按冻结微状态筛选：`trend_continuation + bullish + overheated + 强 + medium`。
3. 使用冻结历史训练向量拟合日期等权 K30，并输出预测收益、下跌概率、上涨 5% 概率、尾部亏损概率和 Q10。
4. 保留全部满足 `pred_return > 0`、`pred_tail_loss5 <= 0.10`、`pred_q10_return >= -5` 的候选，不设上限。
5. 候选保留原有统一综合分。报告把 H4 作为独立视图，同时让同一股票按现有主推规则正常参与主推，不因 H4 身份强制观察或额外加分。
6. 报告 JSON 写入 `h4_t3_pool`，包含策略版本、模型日期、诊断、失败原因和候选预测值。

## 当日增量补算

提供只处理既有日报 JSON 的增量入口。它读取 `docs/data/2026-08-20.json` 中已经生成的 `picks_fusion`，只新增 H4 池并重建报告工作区/页面数据，不重新抓行情、不重跑全市场分析，也不改变其他池的原始结果。

## 错误和空选

- 没有微状态候选或没有候选通过三项门槛时，状态为成功空选，并记录各阶段数量。
- 模型缺失、模型结构错误或特征无法计算属于技术失败，任务必须报错，不得伪装成空选。

## 验收

- 生产向量和预测结果与冻结研究实现对齐。
- H4 无数量上限；全部过门候选都进入 H4 池。
- H4 候选使用现有统一分参与主推，H4 不额外加分。
- 每日 `run.py` 产出包含 `h4_t3_pool`。
- 8 月 20 日从既有数据增量补算成功，JSON 和页面可见且其他池数量不变。
- 相关测试、语法检查和一次真实增量运行通过后提交 MR 到 `main`。
