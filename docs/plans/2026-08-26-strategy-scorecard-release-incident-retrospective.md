# 2026-08-26 选股与记分牌不可用版本发布事故复盘

## Overview

**覆盖范围：** 2026-08-26 收盘日报首次发布至修复版上线

**复盘日期：** 2026-08-26

**形式：** 事实时间线 + 根因树 + Start / Stop / Continue

**严重性：** 内部 P1。页面仍可访问，但选股池边界、策略输入健康和记分牌状态无法被用户可靠解释，辅助决策价值失效。系统不执行自动交易，因此没有自动成交损失。

### 参与角色

- 用户：业务口径与最终决策负责人。
- Codex 主任务：运行链诊断、修复、发布与证据收口。
- 语义审查 agent：池边界、正式样本与记分牌合同复核。
- 信息架构审查 agent：整页信息、事故追溯与变量到 Tab 映射复核。
- UX / 可访问性审查 agent：状态辨识、移动端与对比度复核。

### 事故摘要

2026-08-26 15:09 自动日报提交 `5c84d596` 后，页面出现“影子评测暂时不可用”、策略记分为 0、策略池角色不清等问题。问题不是简单的“T+3 还没到期”：历史行情与到期样本可以读取，但发布流水线在账本 finalizer 之后没有重新生成页面记分牌；同时旧校验器没有验证逐策略输入健康、`picks_pure` 共同上游、记分牌分母和最终页面投影。结果是任务、提交和 Pages 都成功，用户看到的页面却无法回答“这是零收益、等待到期、正常空选，还是数据不可用”。

修复版 `805de5bc` 于 22:38 提交，Pages 部署于约 22:40 完成。修复没有重跑或伪造收盘选股，原始候选池与正式发布摘要的保护 SHA 前后一致。

## What to Improve

### Stop

- 停止把命令退出码、提交成功或 Pages HTTP 200 当成业务可用证明。
- 停止用一个 `0` 同时表示零收益、未成熟、正常空选、策略未启用和数据不可用。
- 停止在 finalizer 后不重建页面就直接提交日报。
- 停止让缺少 `selection_input_health` 的旧快照继续贡献正式成绩。

### Start

- finalizer 后必须从不可变账本和行情库重建 scorecard，再进入发布事务。
- 正式发布必须逐策略验证 `status=verified` 且 `formal_actions_allowed=true`；事故修复只允许登记完整且正式视图已封闭的窄例外。
- 所有策略输出必须满足 `codes ⊆ picks_pure`，但各策略继续使用自己的门槛、排序和空选逻辑。
- 发布验收必须解析真实 `docs/data/<date>.json` 和 `comparison-index.json`，不能只验证生成函数。
- Pages 部署后必须比较远端 main SHA、线上静态资源 SHA 和线上业务字段。

### Continue

- 继续使用信号日收盘入场、T+1/T+3/T+5 收盘评估，并同时展示 MFE、MAE 与盘中 `+5%` 触及。
- 继续将正式推荐、基础候选、研究策略和门控诊断分区，不做跨角色平均收益。
- 继续保留事故前原始证据，但列表、详情和图表都必须标为“仅追溯”。

## Discussion Notes

### 讨论主题一：为什么历史行情存在，页面仍然显示 0 / 暂不可用

**讨论结论：** 行情是否存在与页面是否使用终局账本重新计算是两件事。上次发布只完成了前者，没有完成 finalizer 后的页面重建。

**根因：** 发布顺序错误，finalizer 固化账本后直接发布旧页面投影。

**已采用方案：** finalizer 后从不可变账本与行情库重建 scorecard、比较索引和所有公开页面，再进入原子发布事务。

### 讨论主题二：为什么自动任务和 Pages 都成功，却没有拦住

**讨论结论：** 当时的绿色状态只证明脚本、文件和静态托管成功，不证明决策语义成立。

**根因：** 校验器没有覆盖共同上游、逐策略输入健康、记分牌分母、历史正式样本与最终页面语义。

**已采用方案：** 把这些合同加入正式发布校验，并把真实浏览器和 Pages 实值 SHA 纳入“五证验收”。

### 直接技术根因：发布顺序错误

旧 `daily_run.sh` 在日报生成和校验后执行 `finalize_recommendation_ledger.py`，随后直接调用发布逻辑。finalizer 只固化账本，没有重建已经生成的日报 scorecard。因此，即使三天前行情已经存在，页面也可能继续显示生成时的 pending、0 或不可用状态。

正确顺序现在固定为：

1. 生成正式日报与 provisional 账本。
2. 校验正式行情、池合同和逐策略输入健康。
3. finalizer 固化当日账本成员。
4. 从固化账本与行情库重新计算 scorecard 和比较索引。
5. 原子写入日报、聚合 JSON、根页面、归档页面、JS/CSS 与比较索引。
6. 再次校验正式产物后提交与推送。

### 系统性根因：发布校验覆盖的是“文件存在”，不是“决策语义成立”

旧校验器主要检查市场行情、官方日期和基本页面合同，没有强制验证：

- `picks_pure` 是否为所有策略的共同上游全集。
- 每个策略是否有独立且不矛盾的输入健康证明。
- 15min / 30min 证据是否属于报告交易日并已终局。
- scorecard 是否区分当日运行、账本累计、收益合同样本和事故排除。
- 跨日比较是否只接收健康的正式主推 / H4 样本。
- 用户打开的最终页面是否仍把事故前评分包装成当前信号。

因此，原有绿色状态只能证明“脚本跑完并生成了文件”，不能证明“页面可用于决策”。

### 促成因素

1. **池角色没有冻结。** `picks_pure`、融合池、研究池和混合观察榜的关系在页面与代码中不一致。
2. **健康状态粒度过粗。** 全局状态无法表达融合故障但 H4 健康，或 H4 自己上游错误的情况。
3. **分母语义折叠。** 一个“信号数/0 分”覆盖多种生命周期状态，导致用户无法判断对错。
4. **历史兼容过于乐观。** 缺少新健康字段的旧快照仍可能进入比较与记分牌。
5. **验收偏代码侧。** 单元测试覆盖函数，但缺少“真实正式快照 + finalizer 后重建 + 浏览器整页 + 线上 SHA”的完整链路。

### 不是根因的事项

- 不是因为 T+3 必须等到当天才能读取；已到期的历史信号可以直接从交易日历和行情库回算。
- 不是候选数量太多；数量不设上限，页面只做渐进渲染。
- 不是实际交易价格问题；本项目研究口径固定为信号日收盘价，实际成交不在本次范围。

### “五证验收”完成标准

1. **Git 证据：** `origin/main` 是提交的祖先；推送后远端 main SHA 等于发布提交。
2. **回归证据：** 全量测试、JS 语法、Python 编译、Shell 语法和 `git diff --check` 全绿。
3. **正式数据证据：** `validate_today_report.py` 针对真实 `docs` 通过；原始池保护 SHA 前后一致；修复器第二次运行无新增修复。
4. **页面证据：** 1280px 与 390px 实际浏览器检查；每个 Tab 显示来源、角色、状态、数量和动作权限；事故样本全层“仅追溯”。
5. **线上证据：** Pages 部署成功后，线上首页、JS、CSS、日报 JSON、比较索引与提交内文件 SHA 一致，并解析关键业务字段复核。

任一证据缺失，只能写“候选实现 / 本地验收”，禁止写“已上线可用”。
